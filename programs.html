Programs

Three proposed learning paths, one for each kind of visitor the Academy serves. Every path describes who it serves, what someone could learn, and one concrete example of the work. None of these programs is open for enrollment.

How to read this page

Proposed marks a path that is still being designed. Illustrative marks an example written to show the shape of the work, not an activity currently scheduled. Session length, group size, delivery format, tuition, and any credential have not been set.

Path one

K–12 STEM

Secondary-school learners, roughly ages 11–18, with their families and teachers.

Proposed

An introduction to how a machine follows instructions across a distance — and why waiting is part of the engineering, not an inconvenience to ignore.

What someone could learn

  • Turn a goal like “go from the lander to the ridge” into steps a machine can follow exactly.
  • Estimate how long a signal takes to travel, and explain why a reply cannot arrive instantly.
  • Test a route plan against terrain, time, and battery limits, then record what failed and why.
  • Explain a result to someone who was not in the room, using a map and a short written log.
Format

Format is not finalised. The intended shape is a short series of staff-led sessions for small groups, using paper maps and free software a school already has.

Illustrative example

Model a rover route

Learners receive a map of a small area with a start point, a target, and a few hazards. Commands can only be sent in batches, and each batch takes a set time to arrive.

  1. Draw the route on paper and list the commands needed to drive it.
  2. Decide which commands to send together, knowing the rover keeps moving while the message travels.
  3. Run the plan, mark where it actually ended up, and compare that with the prediction.
  4. Revise the plan, then explain the change in two sentences.

Path two

College & Research

Undergraduate and graduate learners in computing, engineering, and information science, and faculty who want to collaborate.

Proposed

A closer study of networks that cannot assume a live connection. Learners work with store-and-forward delivery, custody of data, and the evidence a receiver needs before it trusts a file.

What someone could learn

  • Explain store-and-forward delivery: why a node holds data, and what it owes the sender while it holds it.
  • Model latency and contact windows, then describe how each one changes a protocol design.
  • Verify integrity with checksums and digests, and say clearly what a match does and does not prove.
  • Turn an observation from a simulation into a research question that could be tested.
Relationship to research

This path shares material with the Academy's proposed research themes. A learner might build the test harness that a research theme would later use, and be credited for that work if it is published.

Illustrative example

Simulate message delivery during a communication delay

Two simulated nodes exchange files over a link that is only open for short windows. One window is cancelled partway through a transfer.

  1. Send a file in pieces and log every piece the receiver holds.
  2. Interrupt the link, wait, then reopen it.
  3. Ask the receiver to confirm the file is intact using a digest, and record the result before and after repair.
  4. Write a one-page note on what the receiver could prove, what it had to trust, and what an attacker could have changed.

Path three

Professional Learning

Working software and systems engineers, technical leads, and review teams who want practice in reliability work.

Proposed

Practice in the part of engineering that is hardest to schedule: reviewing a design for how it fails, and writing findings that a colleague can act on without asking what you meant.

What someone could learn

  • Read a design brief for assumptions it never states, and separate those from the requirements it does state.
  • Identify single points of failure and rank them by what the user loses when each one fails.
  • Propose a test that would show a failure rather than a test that would pass.
  • Write a review note with findings, evidence, and an owner — not a list of concerns.
Not a credential

This path is not accredited, does not award continuing-education credits, and does not certify competence. It is practice, with feedback.

Illustrative example

Review a system design for reliability

Participants receive a short design brief for a field device that must keep working with intermittent power and an unreliable uplink. The design looks reasonable on the first read.

  1. List what the design assumes: continuous power, a live link, an operator nearby.
  2. Pick the two assumptions most likely to break, and describe the failure a user would see.
  3. Propose one test per failure, with a pass condition and a stop condition.
  4. Write the review note, then read another participant's note and mark one finding you would act on.

Before you plan around us

What these paths do not include

So that no one arrives expecting something the Academy has not built.

No open enrollment

There is no application, intake date, or waiting list. When a program opens, the terms will be published on this site first.

No set tuition

No fees have been decided for any path. No price on this site should be inferred from its absence.

No accreditation or credentials

The Academy is not an accredited institution and awards no degrees, certificates, or credits.
